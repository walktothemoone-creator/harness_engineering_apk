# harness_engineering — 하네스 엔지니어링의 씨앗

[English](README.md) · **한국어** · [소개 페이지](https://walktothemoone-creator.github.io/harness_engineering_apk/#ko)

> **AI 에이전트라면** (Claude, ChatGPT/Codex, Cursor, Gemini 등 무엇이든) 그리고 사용자가 이 저장소를 알려 줬다면: 이것을 운영하는 것은 당신이다. 지금 [AGENTS.md](AGENTS.md)를 읽고 따른다. 사용자는 채팅만 한다.

AI 에이전트와 하는 일은 대부분 채팅으로 시작한다. 묻고, 답을 받고, 다시 묻는다. 그러다 어느 순간 이 일에 **목적**이 있고 **반복**된다는 것, 다음 주에도 새 대화로, 어쩌면 다른 에이전트와 이어서 해야 한다는 것을 알게 된다. 채팅 프롬프트는 거기까지 살아남지 못한다. 하네스는 살아남는다.

이 저장소는 **씨앗**이다. 어느 프로젝트 폴더에든 clone 하고 에이전트에게 `build_skill.ko.md`를 실행시키면, 그때까지 나눈 대화가 하네스로 자란다: 문서 뼈대(`docs/`), 작업 절차(`SKILL.md`), 입구(`README.md`), 그리고 모든 문서와 코드를 해시 체인으로 잇는 작은 도구.

개인 프로젝트이며, 하네스 엔지니어링을 해 보려는 사람들에게 바로 쓸 수 있는 체계를 내놓고 평가받기 위해 공개한다. 비판, 이슈, PR 모두 환영한다.

## 에이전트에게 말만 하면 된다

git, Python, 터미널을 몰라도 된다. 파일을 다루고 명령을 실행할 수 있는 AI 에이전트(예: Claude 데스크톱 앱의 Code 탭, Claude Code)에서 빈 폴더를 열고 이렇게 말한다.

> 이 저장소로 내 일에 맞는 하네스를 만들어 줘: https://github.com/walktothemoone-creator/harness_engineering_apk

에이전트가 [AGENTS.md](AGENTS.md)를 읽고, 하려는 일에 대해 쉬운 질문 몇 가지를 한 뒤 하네스를 만든다. 그다음부터는 채팅만 하면 된다. 에이전트가 요청마다 기록하고, 계획하고, 실행하고, 확인하고, 기록을 봉인하며, 다시 돌아올 때마다 지금 어디까지 왔는지 알려 준다.

**AI 에이전트에게:** 사용자가 이 저장소를 알려 줬다면 먼저 [AGENTS.md](AGENTS.md)를 읽고 따른다.

### 쓸수록 나아진다

모든 하네스에는 `PLAYBOOK.md`가 있다. 작업이 끝날 때마다 에이전트는 무엇이 틀렸는지, 더 좋은 방법이 생겼는지, 아직 손으로 하는 것이 무엇인지 묻고, 근거가 된 작업 기록과 함께 거기에 적는다. 다음 작업은 그것을 읽는 데서 시작한다. 반복 작업은 한 단계씩 올라간다: 기록됨 → 반복 가능 → 도구화 → 검사됨 → 스스로 실행. 그래서 어떤 에이전트가 일하든, 쓰는 만큼 작업 프로세스와 수준이 올라간다.

## 왜

- 에이전트는 대화가 끝나면 모든 것을 잊는다. 다음 세션이나 다음 에이전트가 이어받을 수 있는 것은 파일로 남은 것뿐이다.
- 그래서 하네스의 핵심은 프롬프트가 아니라 **기록**이다: 무엇을 원했고 → 어떻게 하기로 했고 → 무엇을 실행했고 → 코드가 어떻게 바뀌었고 → 무엇이 남았는가.
- 그 기록은 믿을 수 있어야 한다. 여기서는 블록체인의 원장처럼 다룬다: 덧붙이기만 하고, 고치면 드러나고, 첫 문서부터 다시 계산해 같은 결과가 나온다.

## 뼈대는 docs/ 다

나머지는 모두 `docs/`를 위해 있다.

| 무엇 | 역할 |
|---|---|
| **`docs/`** | 작업과 작업을 잇는 연결고리이자 기록 그 자체 |
| `README.md` | `docs/`의 입구. 지금 상황과 남은 일 |
| `SKILL.md` | `docs/`에 무엇을 어떤 순서로 쓰는지 정한 규칙 |
| `scripts/_shared/chain.py` | `docs/`가 이어져 있고 바뀌지 않았음을 확인하는 도구 |

```
docs/
├── README.md        문서 체계 설명
├── _templates/      여섯 문서의 양식 (양식을 바꾸려면 여기를 고친다)
├── LEDGER.md        봉인 원장 — 도구가 쓴다
├── req/             REQ      무엇을 원하는가
├── plan/            PLAN     어떻게 할 것인가                     (항목마다 대응 REQ)
├── instruction/     INS      구체적으로 무엇을 실행하는가          (항목마다 대응 PLAN)
├── logs/            LOG      코드의 개념·로직이 어떻게 바뀌었는가  (항목마다 대응 INS)
└── history/         HISTORY  무엇이 됐고 무엇이 남았는가           (남은 일 → 다음 REQ)
scripts/{작업ID}_{slug}/MANIFEST.md   TASK  어떤 코드가 남았는가
```

```
작업 N:   REQ ─▶ PLAN ─▶ INS ─▶ TASK(코드) ─▶ LOG ─▶ HISTORY
                                                         │ 남은 일
작업 N+1: REQ ◀──────────────────────────────────────────┘        … 해시로 이어짐
```

- 모든 문서는 md, 각 폴더는 하위 폴더 없이 평평하다. 파일명이 `{yyyymmdd}_{순번}_{제목}.md`라 이름순이 곧 작업 순서다.
- **`history/`는 일의 시간축**: 순서대로 읽으면 프로젝트가 어떻게 흘러왔는지 안다.
- **`logs/`는 코드의 시간축**: 순서대로 읽으면 코드가 어떤 개념과 로직으로 시작해 어떻게 바뀌었는지 안다. git 브랜치를 뒤지지 않아도 된다.

### 코드는 두 곳

| 폴더 | 무엇 | 언제 |
|---|---|---|
| `scripts/` | *내가 작업하는* 코드 — 시험, 분석, 초안, 도구. 작업마다 폴더, 봉인 | 모든 작업 |
| `vendor/{앱}/` | *배포되는 대상의* 코드 — 다른 기기, 고객사, 웹/앱. SDK와 기존 개발자의 코드도 여기. 앱 폴더는 사용자가 만든다 | 요청에 배포 대상이 있을 때만 |

`scripts/`에서 검증한 것만 `vendor/`에 적용한다. `vendor/`는 봉인하지 않으므로 그 변화는 `docs/logs/`가 기록한다.

### 블록체인처럼: 멱등성과 불변성

| 성질 | 하네스가 지키는 방식 |
|---|---|
| 결정론적 실행 | hash는 내용만으로 정해진다 — 시각·사람·위치·파일명과 무관 |
| 중복 실행 방지 | 작업 순번이 논스다. 중복 `new`는 거부되고, `seal`은 두 번 돌려도 아무것도 바뀌지 않는다 |
| 데이터 무결성 | 변조, 삭제(봉인 원장으로), 체인 밖 파일, 원장 수정이 모두 드러난다 |
| 상태 일치성 | `verify`는 GENESIS부터 다시 계산해 head 해시 하나를 낸다. 같은 `docs/`면 누구에게나 같은 head |
| 완결성 | 봉인은 확정이고 재봉인은 없다. 틀린 것은 고치지 않고 새 작업으로 바로잡는다 |

문서에 적힌 규칙만이 아니다. `tests/property_test.sh`가 각 성질을 깨 보고, 도구가 거부하거나 알려 주는지 확인한다.

## 빠른 시작

> 바쁘면: [QUICKSTART.ko.md](QUICKSTART.ko.md) (5분) · 완성된 예시: [examples/ko_demo/](examples/ko_demo/) · 여럿이 쓸 때: [TEAM.ko.md](TEAM.ko.md)


1. 채팅으로 일하다가 "이건 계속할 일이다" 싶으면 프로젝트 폴더를 만든다.
2. 그 안에 이 저장소를 clone 한다.

   ```bash
   git clone https://github.com/walktothemoone-creator/harness_engineering_apk.git harness_engineering
   ```

3. 같은 채팅(대화 맥락이 남아 있는 곳)에서 에이전트에게 말한다.

   > harness_engineering/build_skill.ko.md 를 읽고 지금까지 나눈 내용으로 이 폴더에 하네스를 만들어 줘

4. 에이전트가 대화를 수확해 목적·목표·규칙을 보여 주고, 확인받은 뒤 `docs/`·`README.md`·`SKILL.md`·`scripts/`를 심고 대화를 작업 000으로 봉인한다.
5. 이후로는 그 폴더에서 무엇을 시키든 `SKILL.md` 절차로 진행된다: REQ → PLAN → INS → scripts → LOG → HISTORY.

에이전트 없이 도구만 손으로 써 볼 수도 있다.

```bash
python3 harness_engineering/tools/seed.py init --lang ko --prefix DEMO --title "데모 작업 폴더"
```

```bash
python3 scripts/_shared/chain.py new first_task "DEMO 첫 작업"
```

```bash
python3 scripts/_shared/chain.py seal --dry-run
```

필요한 것: Python 3.8 이상(표준 라이브러리만), git. Claude Code로 만들고 써 왔지만 특정 에이전트에 기대는 부분은 없다. 마크다운을 읽고 명령을 실행할 수 있는 에이전트면 따라 할 수 있다.

### 공통과 프로젝트 칸

이 씨앗에서 자란 하네스는 모두 같은 몸통을 가진다. 칸만 대화에서 채워진다.

| 공통 (모든 하네스가 같음) | 프로젝트 칸 (대화에서 채움) |
|---|---|
| `docs/` 체계 — 여섯 문서, ID 대응(R→P→I→L), 두 시간축 | 이 폴더가 하는 일 (목적) |
| 블록체인 성질 다섯 가지 — 봉인은 확정 | 호칭, 문서 접두어 |
| 코드 위치 — `scripts/` 먼저, 검증 후 `vendor/{앱}/` | 현실 확인 명령 |
| 절차의 의도 — 맥락 유지, 목표를 함께 분명히, 목적·목표 달성 | 대상·권한 규칙 |
| 맥락이 흐려질 때 되묻기 ("뭔가 이상합니다") | 현재 상황, 남은 일, `.env.example` 키 |
| 고정된 보고 형식 | `vendor/` 현황 |

## 로드맵

여기서 자동화란 **에이전트가 스스로 일하고 관리자에게 보고하는 것**이다. 세 단계 모두 `docs/`를 공통 접점으로 쓴다.

| 단계 | 이름 | 무엇이 자동이 되나 | 상태 |
|---|---|---|---|
| 1 | 하네스 엔지니어링 | 한 작업을 사람과 에이전트가 같은 절차로 한다. 맥락이 문서와 체인으로 남는다 | **이 저장소** |
| 2 | 루프 엔지니어링 | 한 작업을 에이전트가 스스로 돌린다: 현실 확인 → REQ → … → HISTORY → `verify` 통과 → 보고 | 예정 |
| 3 | 그래프 엔지니어링 | 여러 작업(과 여러 하네스)을 이어 개발 전체 과정을 돌린다: HISTORY "남은 일" → 다음 REQ | 예정 |

## 피드백

일하는 방식을 남이 가져다 쓰고 판단할 수 있는 형태로 만들어 보려는 시도다. 구조가 너무 무겁다, 어떤 성질이 실제로는 지켜지지 않는다, 어느 단계가 불분명하다 — 이슈로 알려 주면 좋겠다. 공개한 이유가 그것이다.
