## 이 절차의 의도

이 절차는 **맥락을 유지하면서, 에이전트와 사용자가 목표를 분명히 다잡아 가며, 목적과 목표를 달성하기 위한 것**이다. 문서를 채우는 것이 목적이 아니다.

- **맥락 유지**: 대화가 끊기거나 다른 에이전트가 이어받아도 "무엇을 원했고 → 어떻게 하기로 했고 → 실제로 무엇을 했고 → 무엇이 남았는지"가 문서와 체인으로 이어진다. 그래서 매번 README부터 읽고, 끝날 때 README를 고친다
- **목표를 함께 분명히**: 목표는 에이전트가 혼자 정하지 않는다. 요청을 받으면 목적(왜 하는가)과 목표(무엇이 되면 끝인가)를 글로 적어 사용자와 맞추고, 진행 중에 어긋나면 다시 맞춘다
- **목적·목표 달성**: 계획·지시·코드·보고의 모든 항목은 그 목표로 거슬러 올라갈 수 있어야 한다. 보고는 "무엇을 했다"가 아니라 "목표가 달성됐는가"로 한다

단계마다 무엇을 쓸지 망설여지면 이 세 가지에 도움이 되는 쪽을 고른다.

**뼈대는 `docs/`다.** 작업과 작업을 잇는 연결고리이자 기록이 거기에 쌓인다. 이 문서는 `docs/`에 무엇을 어떤 순서로 쓰는지 정한 규칙이다. 문서 여섯 종류의 역할과 이어지는 방식은 [docs/README.md](docs/README.md)에 있다.

## 맥락이 흐려질 때 — 사용자에게 되묻는다

목표를 지키는 것은 에이전트의 일이기도 하다. 사용자의 말이 지금까지의 목적·목표와 이어지지 않거나, 어긋나거나, 무엇을 위한 것인지 알 수 없으면 **그대로 따르지 말고 먼저 피드백한다.** 조용히 따라가면 맥락이 끊기고 목표가 흐려진다.

이럴 때 되묻는다.
- 요청이 진행 중인 작업의 목표와 관계가 없거나 반대 방향이다
- 앞서 정한 것과 모순된다 (범위, 대상, 하지 않기로 한 일 등)
- 무엇이 되면 끝인지 알 수 없다
- 에이전트 자신이 지금 무엇을 위해 일하고 있는지 설명할 수 없게 됐다

피드백에는 세 가지를 담는다.
1. 이상하다는 신호 — "{{USER_CALL}}, 뭔가 이상합니다."
2. 지금까지의 목적과 목표 — "지금까지 목적은 …이고, 목표는 …입니다." (README와 진행 중인 REQ 기준으로 한두 문장)
3. 질문 — "이 요청의 목표가 무엇인가요? 맥락이 불분명해집니다." 가능하면 선택지를 준다: 기존 목표를 바꾸는 것인지, 별개의 새 작업인지, 잠깐의 곁가지인지

답을 받으면 그에 맞게 처리한다: 목표를 바꾸는 것이면 REQ를 고치고(봉인 전), 새 작업이면 2단계부터 새로 시작한다. 가벼운 질문이나 상태 확인처럼 목표와 충돌하지 않는 말에는 되묻지 않고 답한다.

작업 위치: 이 파일이 있는 폴더 (`{{PROJECT}}/`) — 아래 명령은 모두 여기서 실행

## 사용자는 채팅으로만 일한다

사용자는 명령, 문서 체계, 체인을 몰라도 된다. 사용자는 말하고, 정리는 당신이 한다.

- 명령은 `chain.py`를 포함해 모두 당신이 실행한다. 비밀번호 입력이 필요한 명령이 아니면 사용자에게 명령을 치라고 하지 않는다
- 명령이 실패하면 원인을 찾아 직접 고치고, 무슨 일이 있었는지 쉬운 말 한두 문장으로 알린다
- 채팅에서는 쉬운 말을 쓴다("저장하고 잠갔습니다", "기록이 온전합니다"). ID, 해시, 문서 이름은 문서에 둔다. 10단계 보고는 정해진 형식을 지킨다
- 대화가 시작되면(사용자가 돌아오면) 묻기 전에 README를 바탕으로 지금 어디까지 왔고 무엇이 남았는지 두세 문장으로 알린다
- 사용자만 답할 수 있는 것만 묻는다: 목적, 무엇이 되면 끝인지, 선택, 위험한 일의 승인. 나머지는 정하고 기록한다

## 언제 이 절차를 쓰나

- 코드를 만들거나 고칠 때, 대상을 조사·조치할 때, 문서를 새로 낼 때 → **전체 절차**
- 질문에 답하거나 상태만 조회할 때 → 1단계(README 읽기)만 하고 답한다. 문서를 만들지 않는다
- 요청이 기존 작업의 작은 후속인지 새 작업인지 모호하면 새 작업으로 잡는다 (봉인된 문서는 고칠 수 없기 때문)

## 코드가 놓이는 곳 — scripts/ 와 vendor/

코드는 두 곳에 나뉜다. 섞지 않는다.

| 폴더 | 무엇 | 누가 만드나 | 체인 |
|---|---|---|---|
| `scripts/{작업ID}_{slug}/` | **내가 작업하는 코드** — 시험, 조사·분석, 초안, 도구 | 에이전트가 작업마다 | MANIFEST `tree_hash`로 봉인 |
| `vendor/{앱}/` | **배포되는 대상의 코드(application)** — 다른 기기, 고객사, 웹/앱에 올라가는 것. SDK와 기존 개발자의 코드도 여기 | 폴더는 **사용자가** 만들고 SDK 등을 넣어 둔다 | 봉인하지 않는다(계속 자라는 코드). 변화는 LOG로만 추적한다 |

- **vendor는 특별한 요구사항이 있을 때만 다룬다.** 채팅이나 REQ에 "다른 기기에 적용", "웹/앱에 배포", "고객사에 전달"처럼 배포 대상이 있을 때다. 그런 요구가 없는 작업은 `scripts/`에서 끝난다. `vendor/` 폴더 자체도 그런 요구가 생기기 전에는 없다
- **먼저 scripts, 그다음 vendor.** `scripts/`에서 시험과 분석으로 충분히 검증하고(MANIFEST 검증 상태 ✅) 구조가 어느 정도 완성된 것만 `vendor/{앱}/`에 적용한다. 검증 안 된 초안을 vendor에 바로 쓰지 않는다
- **vendor 작업은 scripts를 참고해서 한다.** 어느 작업의 어느 파일을 바탕으로 했는지 LOG에 적는다
- `vendor/` 바로 아래의 앱 폴더를 에이전트가 임의로 만들지 않는다. 필요한데 없으면 사용자에게 폴더 이름과 그 안에 둘 것(SDK, 기존 코드)을 묻는다. 사용자가 만들라고 한 경우에만 만든다
- 사용자가 넣어 둔 SDK와 기존 개발자의 코드는 원본이다. 고치기 전에 무엇이 원본이고 어디서 왔는지(저장소·커밋·버전)를 그 앱 폴더의 `README.md`와 LOG에 적는다 (양식: `docs/_templates/vendor_app.md`)
- vendor에 적용하는 것과 실제로 배포하는 것은 다르다. 배포(기기에 넣기, 웹/앱에 올리기, 남의 저장소에 push)는 계획 단계에서 사용자 확인을 받는다

## 절차

### 1. README.md를 읽는다

`README.md`의 "현재 상황"과 "남은 일"을 확인하고, 이어서 `PLAYBOOK.md`를 읽는다: 이번 일과 같은 종류의 방법과 품질 기준이 적혀 있으면 그대로 따른다. 배경이 더 필요하면 `docs/history/`를 작업 순서대로 읽는다 (`python3 scripts/_shared/chain.py list history`). 코드가 어떻게 변해 왔는지는 `docs/logs/`를 같은 순서로 읽는다 (`list logs`). 이어서 체인이 온전한지 본다.

```bash
python3 scripts/_shared/chain.py verify
```

실패하면 작업을 시작하기 전에 사용자에게 알린다. 누군가 봉인된 문서나 코드를 고쳤다는 뜻이다.

**현실 확인:** README "현재 상황"에는 기준 시각이 있다. 그 뒤로 바깥 현실(다른 사람의 배포, 설정 변경 등)이 바뀌었을 수 있다. 외부 대상이 걸린 작업이면 시작 전에 아래를 조회해 README와 다른 점을 찾고, 다르면 사용자에게 먼저 알린다.
- <!-- FILL: 현실 확인 명령. 예: 서버/장비 상태 조회, 남의 저장소 최신 커밋, 외부 저장소 목록. 없으면 "외부 대상 없음 — 생략" -->
- 이 폴더에서 바뀐 파일: `find . -newer docs/history/<가장 최근 HISTORY> -type f -not -path './.venv/*' -not -path './vendor/*' -not -path './harness_engineering/*'`

### 2. 요청을 파악한다 — REQ

요청은 채팅 또는 `docs/inbox/`에 미리 놓인 문서에서 온다 (`docs/req/`에는 도구가 만든 REQ만 둔다 — 다른 파일이 있으면 `verify`가 실패한다). 먼저 이 요청을 다루는 작업이 이미 있는지 본다 (`python3 scripts/_shared/chain.py status`). 봉인 안 된 작업이 있으면 그것을 이어서 쓰고, 이미 봉인된 작업이 같은 요청을 끝냈으면 새로 만들지 않고 그 HISTORY를 알려 준다. 없을 때만 새 작업 뼈대를 만든다 (순번은 자동, 같은 제목·slug의 미봉인 작업이 있으면 도구가 거부한다).

```bash
python3 scripts/_shared/chain.py new <slug> "<제목>"
```

- `<slug>`: 영문 소문자·숫자·밑줄의 짧은 이름. `<제목>`: 문서 제목. 제목은 `{{PREFIX}}_`로 시작한다 (예: `"{{PREFIX}} 무엇을 하는 작업"`)
- 여섯 파일이 생긴다: `docs/req|plan|instruction|logs|history/{yyyymmdd}_{순번}_{제목}.md`, `scripts/{yyyymmdd}_{순번}_{slug}/MANIFEST.md`. 본문 양식은 `docs/_templates/`에서 온다
- `docs/inbox/`에 사용자가 넣어 둔 요청 문서가 있으면 그 내용을 REQ의 "요청 원문"에 옮기고 출처 파일명을 적는다. inbox 파일은 체인 밖이라 그대로 두어도, 지워도 된다

REQ에 쓸 것: 배경(**목적**: 왜 하는가, **목표**: 무엇이 되면 끝인가, **배포 대상**: 없음 또는 `vendor/{앱}/`) / **요청 원문(그대로 인용)** / 요구사항 표(R1, R2 … 와 수용 기준) / 범위 밖·제약.

요청에 다른 기기 적용·웹/앱 배포·고객사 전달이 들어 있으면 배포 대상을 `vendor/{앱}/`으로 적고, 그렇지 않으면 "없음(scripts에서 끝남)"이라고 적는다. 어느 쪽인지 모호하면 묻는다.

여기서 사용자와 목표를 맞춘다. 파악한 목적과 목표를 한두 문장으로 사용자에게 말하고 작업을 시작한다. 요청이 두 가지로 읽히거나, 목표를 달성했는지 판단할 기준이 없으면 계획을 세우기 전에 묻는다. 직전 HISTORY의 "남은 일"과 이번 요청이 어떻게 이어지는지도 배경에 적는다.

### 3. 작업계획서 — PLAN (`docs/plan/`)

목표 / 범위(포함·제외) / 작업 분해 표 / 위험과 대응 / 완료 기준.
작업 분해 표의 각 항목(P1, P2 …)에는 **대응 REQ ID**와 검증 방법을 적는다. 어느 REQ에도 대응하지 않는 작업은 넣지 않고, 대응 PLAN이 없는 REQ가 남지 않게 한다.

### 4. 작업지시서 — INS (`docs/instruction/`)

사전 조건 / 작업 절차 표 / 금지·주의 사항 / 중단·복구 기준.
절차 표의 각 항목(I1, I2 …)에는 **대응 PLAN ID**, 실제 실행할 명령이나 대상, 확인 방법을 적는다. 다른 사람이 이 문서만 보고 같은 작업을 할 수 있어야 한다.

### 5. 작업한다 — scripts (`scripts/{yyyymmdd}_{순번}_{slug}/`), 필요하면 vendor (`vendor/{앱}/`)

- 코드는 그 작업의 폴더에만 만든다. 여러 작업이 같이 쓰는 것만 `scripts/_shared/`에 둔다
- **사용자에게 줄 결과물**(보고서, 요약, 초안 등 사용자가 열어 보거나 전달할 것): 작업 폴더에 만들어 봉인되게 하고, 사용자가 알아볼 쉬운 이름으로 `outputs/`에 사본을 둔다. 사용자에게는 `outputs/` 경로를 알려 준다. 코드가 없는 작업에도 결과물은 있다: MANIFEST에 적는다
- **입력 파일**(사용자가 `docs/inbox/`에 넣은 것)은 그 자리에 둔다. 개인정보나 기밀이 있을 수 있는 원본을 `scripts/`나 문서에 복사하지 않는다 — 봉인하면 영구히 남는다. 결과를 입력까지 따라갈 수 있게 INS에 입력 파일명과 SHA-256을 적는다
- **반복 작업**: 같은 방법이 두 번째로 필요해지면 그 실행은 평소대로 끝내고, 방법을 공용 도구로 만들자고 사용자에게 제안한다. 동의하면 별도 작업으로 한다: 스크립트와 시험을 `scripts/_shared/`에 두고, 그 뒤로는 복사하지 않고 불러 쓴다
- **공용 스크립트는 체인 밖**이므로 손으로 지킨다: 작업이 공용 스크립트를 만들거나 고칠 때마다 그 판의 사본을 작업 폴더에 두고(봉인된다) SHA-256을 INS와 LOG에 적는다. 실행을 시작할 때 공용 스크립트의 SHA-256을 마지막으로 적힌 값과 비교하고, 다르면 멈추고 사용자에게 알린다
- 이전 작업의 코드를 고쳐야 하면 그 폴더를 건드리지 말고, 새 작업 폴더에 복사해 고친다 (이전 폴더는 봉인돼 있다)
- 스크립트는 **다시 돌려도 같은 결과**가 되게 만든다(멱등): 이미 된 것은 건너뛰고, 같은 것을 두 번 만들거나 두 번 보내지 않는다. 그렇게 만들 수 없는 것(대상의 상태를 바꾸는 명령)은 MANIFEST에 "재실행 주의"와 다시 돌리기 전 확인할 것을 적는다
- 설정값은 코드에 적지 않고 `.env`에서 읽는다 (`scripts/_shared/envload.py`). 새 키가 생기면 `.env.example`에 설명과 함께 추가한다
- `MANIFEST.md`에 파일마다 하는 일, **대응 INS ID**, 검증 상태(실제로 돌려 봤는지)를 적는다. 코드가 없는 작업이면 "코드 없음"이라고 적는다
- REQ의 배포 대상이 `vendor/{앱}/`인 작업만 vendor를 고친다. 순서는 scripts에서 만들고 검증 → MANIFEST에 검증 상태 ✅ → 그것을 바탕으로 `vendor/{앱}/`에 적용. MANIFEST에 "vendor 적용" 줄(어느 파일이 vendor의 어디로 갔는지)을 남긴다
- 계획과 다르게 진행되면 PLAN·INS를 먼저 고친 뒤 계속한다 (아직 봉인 전이므로 고칠 수 있다)
- 하다 보니 REQ의 목표 자체가 맞지 않거나 달성할 수 없다는 것을 알게 되면, 멈추고 사용자와 목표를 다시 맞춘다. 맞춘 내용은 REQ에 반영한다. 목표를 조용히 바꾸거나 줄여서 끝내지 않는다

### 6. 코드 변경 기록 — LOG (`docs/logs/`)

요약 / 변경 내역 표 / 지금의 로직 / 계보.
이번 작업으로 `scripts/`·`vendor/`의 코드가 **어떤 개념과 로직에서 어떻게 바뀌었는지**를 적는다. git 브랜치를 따라가지 않아도 `docs/logs/`만 작업 순서대로 읽으면 코드의 변화를 추적할 수 있어야 한다.

- 변경 내역 표의 각 항목(L1, L2 …)에는 대상(경로·함수), 종류(신규 / 변경 / 복사 후 변경 / 삭제 / 외부 코드), 이전 → 이후, 왜 바꿨나, **대응 INS ID**를 적는다
- "복사 후 변경"은 어느 작업의 어느 파일에서 왔는지 적는다
- `vendor/{앱}/`을 고쳤으면 종류를 "vendor 적용"으로 하고, 바탕이 된 scripts 작업·파일, 사용자가 넣어 둔 원본(SDK·기존 코드)에서 무엇이 달라졌는지, 배포했는지(언제·어디에)를 적는다. vendor는 봉인되지 않으므로 **LOG가 유일한 추적 수단**이다. 앱 폴더가 git 저장소면 커밋 해시도 적는다
- "지금의 로직"은 코드를 열지 않고도 흐름을 알 수 있게 쓴다 (입력 → 처리 순서 → 출력, 전제)
- "계보"에 직전 LOG의 ID를 적어 한 코드의 변화를 거슬러 올라갈 수 있게 한다
- 코드 변경이 없으면 요약에 "코드 변경 없음"이라고만 쓴다. LOG 문서는 그래도 남긴다
- MANIFEST는 "지금 무엇이 있나", LOG는 "어떻게 여기까지 왔나"다. 실행 출력 같은 원자료는 작업 폴더에 두고 LOG에는 요지만 적는다

### 7. 작업 기록 — HISTORY (`docs/history/`)

요약 / 결과 / **추적표(REQ → PLAN → INS → 결과물 → LOG → 상태)** / 남은 일.
`docs/history/`는 작업 순서대로 쌓이는 이 프로젝트의 이력이다. 이 문서만 읽어도 그 작업에서 무엇이 됐는지 알 수 있게 쓴다.
요약의 첫 문장은 REQ의 목표가 달성됐는지다. 추적표에 모든 REQ ID가 나와야 한다. 못 한 것은 ❌나 ⏳로 남기고 이유를 적는다. "남은 일"은 다음 작업이 이어받을 맥락이므로, 다음에 무엇부터 해야 하는지 알 수 있게 쓴다.

### 8. 체인으로 잇는다

여섯 문서의 `status`를 `완료`로 바꾼 뒤 봉인하고 검증한다.

```bash
python3 scripts/_shared/chain.py seal --dry-run
```

무엇이 확정되는지와 점검 결과(작성 중인 문서, 빠진 문서)를 보고, 여섯 문서를 마지막으로 읽어 본다. 괜찮으면 봉인한다.

```bash
python3 scripts/_shared/chain.py seal
```

"체인 정상 — 문서 N개, head …"가 나와야 끝난다. **봉인은 확정이다. 다시 봉인하는 방법은 없다.** 봉인 뒤에 빠뜨리거나 틀린 것을 발견하면 봉인된 문서를 고치지 말고 새 작업으로 바로잡는다 (그 HISTORY에 어느 문서의 무엇을 바로잡는지 적는다).

### 9. README.md를 마무리한다

`README.md`의 "현재 상황" 표(기준 시각 포함), "남은 일", 작업 목록 표, 이력 표를 고친다. README는 체인 밖이라 자유롭게 고칠 수 있고, **항상 지금 상태를 말해야 한다.**

이어서 `PLAYBOOK.md`를 고친다 — 일이 그저 반복되지 않고 나아지게 하는 단계다. 방금 봉인한 작업에 대해 세 가지를 묻고, 근거가 있는 것만 적는다 (지어내지 않는다. 없으면 고치지 않는다).
1. 무엇이 틀렸거나, 느렸거나, 다시 해야 했나? → "배운 것"에 한 줄, 실수가 빠져나갔다면 "품질 기준"에 확인 추가
2. 이런 종류의 일을 하는 더 좋은 방법이 생겼나? → "반복 작업 — 지금의 방법"을 고친다. 수준은 이번 작업이 증명할 때만 올린다
3. 아직 손으로 하는 것은? → "개선 후보"에 적고, 가장 효과가 큰 하나를 보고에서 사용자에게 제안한다

모든 줄에 근거가 된 HIST ID를 적는다.

### 10. 사용자에게 보고한다

아래 형식으로 보고한다. 이 형식은 나중에 루프(자동 반복)·그래프(여러 작업 연결) 단계에서 관리자 보고로 그대로 쓰이므로 바꾸지 않는다. 채팅으로 일하는 사용자에게는 이 형식 앞에, 무엇이 생겼고 어디서 열어 볼 수 있는지(`outputs/` 경로)를 쉬운 말 한 문장으로 먼저 말한다.

```
목표 달성: ✅ 달성 / ⏳ 일부 / ❌ 미달성 — <목표 한 문장>
한 일: <핵심 결과 1~3줄>
확인 못 한 것: <⏳ 항목과 이유, 없으면 "없음">
남은 일 / 다음 목표 후보: <1~3개, 사용자가 고를 수 있게>
다음 개선 제안: <PLAYBOOK에서 고른 개선 하나, 없으면 "없음">
근거: <HISTORY 파일 링크>
기록: 온전함 / 문제 — 문서 <N>개, 확인값 <head 앞 12자리>
```

## docs/는 블록체인처럼 — 멱등성과 불변성

`docs/`의 기록은 블록체인의 원장처럼 다룬다. **같은 일은 몇 번을 해도 결과가 같아야 하고(멱등), 한 번 확정한 기록은 바뀌지 않아야 한다(불변).** 도구(`chain.py`)가 강제하는 부분과 에이전트가 지켜야 하는 부분이 있다.

| 성질 | 뜻 | 도구가 강제하는 것 | 에이전트가 지킬 것 |
|---|---|---|---|
| 1. 결정론적 실행 | 누가, 언제, 몇 번을 해도 같은 입력에는 같은 결과 | `hash`는 문서 내용만으로, `tree_hash`는 폴더의 파일 내용만으로 계산된다 | 머리말의 `prev`·`prev_hash`·`hash`·`tree_hash`를 손으로 쓰지 않는다. 문서에는 다시 확인할 수 있는 것(명령, 파일, 시각)을 근거로 적는다 |
| 2. 중복 실행 방지 | 같은 일이 두 번 처리되지 않는다 | 작업 순번이 논스다 — 0부터 빠짐·중복 없이 이어져야 한다. 같은 제목·slug의 미봉인 작업이 있으면 `new`를 거부한다. `seal`은 이미 봉인된 문서를 건드리지 않는다 | `new` 전에 이 요청을 다루는 작업이 이미 있는지 본다(`chain.py status`). 봉인 안 된 작업이 있으면 새로 만들지 말고 이어서 쓴다. 이미 끝난 요청을 다시 받으면 새 작업을 만들지 않고 그 HISTORY를 알려 준다 |
| 3. 데이터 무결성 | 위변조·누락이 없어 기록 전체를 믿을 수 있다 | 내용·코드가 바뀌면 hash가, 문서가 지워지면 원장(`docs/LEDGER.md`) 대조가, 체인 밖 파일이 섞이면 폴더 검사가 잡는다 | `docs/req` `plan` `instruction` `logs` `history`에는 `chain.py new`가 만든 문서만 둔다. 메모·초안·원자료는 작업의 `scripts/` 폴더에 둔다. `docs/LEDGER.md`를 손으로 고치지 않는다 |
| 4. 상태 일치성 | 처음부터 다시 실행해도 같은 최종 상태에 도달한다 | `verify`는 저장된 값을 믿지 않고 GENESIS부터 전부 다시 계산해 head(마지막 문서의 hash)를 낸다 | 작업을 시작할 때와 끝낼 때 `verify`를 돌린다. 보고에 문서 수와 head를 적는다 — 다음 사람이 같은 head를 얻는지로 같은 상태인지 안다 |
| 5. 완결성 | 한 번 확정된 것은 영구히 바뀌지 않는다 | 봉인은 확정이다. 다시 봉인하는 기능이 없다. 원장은 뒤에 덧붙이기만 한다. `작성 중`인 문서와 문서가 빠진 작업은 봉인되지 않는다 | 봉인된 문서·코드를 고치지 않는다(오타 하나도). 틀린 것을 발견하면 **새 작업으로 바로잡고**, 그 HISTORY에 어느 문서의 무엇을 바로잡는지 적는다. 그래서 봉인 전에 `seal --dry-run`으로 확인한다 |

봉인 전까지는 자유롭게 고친다. 봉인이 "확정" 버튼이다.

## 체인이 하는 일

```
REQ → PLAN → INS → TASK(MANIFEST + 폴더 안 코드) → LOG → HISTORY → 다음 작업의 REQ → …
```

- 각 문서 머리말의 `prev_hash`는 앞 문서의 `hash`와 같다. `hash`는 그 문서 내용의 SHA-256이다
- MANIFEST의 `tree_hash`는 같은 폴더 안 모든 코드 파일을 묶는다. 코드 한 줄만 바뀌어도 검증이 실패한다
- 머리말(`id`, `work`, `type`, `title`, `date`, `status`, `prev`, `prev_hash`, `hash`)의 `prev`·`prev_hash`·`hash`·`tree_hash`는 도구가 채운다. 손으로 쓰지 않는다
- `docs/LEDGER.md`는 봉인 원장이다. 봉인된 문서의 id·hash를 순서대로 적은 목록으로, 도구만 쓴다
- 체인 밖: `README.md`, `SKILL.md`, `docs/README.md`, `docs/_templates/`, `.env`, `.env.example`, `.gitignore`, `scripts/_shared/`, `.venv/`, `vendor/`, `harness_engineering/`

## 반복을 발견하면

같은 조회·명령·판단을 두 작업 이상에서 손으로 반복했다면 HISTORY "남은 일"에 "자동화 후보"로, `PLAYBOOK.md` "개선 후보"에도 적고 사용자에게 제안한다. 사용자가 동의하면 새 작업으로 `scripts/_shared/`에 만든다 (5단계 "반복 작업"). 이것이 다음 단계(루프 엔지니어링)의 재료가 된다.

## 끝났는지 확인

- [ ] REQ에 목적과 목표가 적혀 있고, 사용자와 맞춘 내용과 같다
- [ ] HISTORY 요약이 그 목표의 달성 여부로 시작한다
- [ ] LOG에 이번 코드 변경이 모두 있고(없으면 "코드 변경 없음"), 각 항목에 대응 INS와 이전 → 이후가 적혀 있다
- [ ] vendor를 고쳤다면: REQ에 배포 대상이 적혀 있고, scripts에서 먼저 검증했고, LOG에 "vendor 적용" 항목과 바탕이 된 scripts가 있다
- [ ] 여섯 문서가 모두 있고 `chain.py status`에 전부 "봉인"으로 나온다
- [ ] 봉인 전에 `seal --dry-run`으로 확인했다
- [ ] `chain.py verify`가 "체인 정상"이고, 문서 수와 head를 보고에 적었다
- [ ] 봉인된 문서·코드를 고치지 않았다. `docs/`의 다섯 폴더에 체인 밖 파일을 두지 않았다
- [ ] HISTORY 추적표에 모든 REQ ID가 있다
- [ ] 새 `.env` 키가 `.env.example`에 있다
- [ ] 사용자에게 줄 결과물이 `outputs/`에 있고, 개인정보가 든 입력 원본을 봉인되는 폴더에 복사하지 않았다
- [ ] `PLAYBOOK.md`를 세 가지 질문으로 점검했고, 바뀐 줄에 HIST ID가 있다
- [ ] `README.md`의 현재 상황(기준 시각)·남은 일·작업 목록이 방금 한 작업과 현실 확인 결과를 반영한다
