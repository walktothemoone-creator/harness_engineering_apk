# docs/ — 작업의 뼈대

이 폴더가 하네스의 핵심이다. 작업과 작업을 잇는 연결고리이고, 무엇을 원했고 무엇을 했는지의 기록이다. `SKILL.md`는 여기에 무엇을 어떤 순서로 쓰는지 정한 규칙이고, `scripts/_shared/chain.py`는 이 기록이 이어져 있고 바뀌지 않았음을 확인하는 도구다.

모든 문서는 md다. 각 폴더는 하위 폴더 없이 평평하고, 파일명이 `{yyyymmdd}_{순번}_{제목}.md`라 **폴더를 이름순으로 보면 곧 작업 순서**다. (`python3 scripts/_shared/chain.py list history`로도 같은 순서를 볼 수 있다.)

## 여섯 문서

한 작업은 문서 여섯 개를 남긴다. 다섯은 이 폴더에, 하나(MANIFEST)는 코드 옆에 있다.

| 순서 | 폴더 | 문서 (ID) | 답하는 질문 | 앞 문서에서 받는 것 | 뒤로 넘기는 것 |
|---|---|---|---|---|---|
| 1 | `req/` | 요구사항 정의서 (REQ) | 무엇을 원하는가 | 직전 작업 HISTORY의 "남은 일", 사용자 요청 원문 | 요구사항 R1, R2 … 와 수용 기준 |
| 2 | `plan/` | 작업계획서 (PLAN) | 어떻게 할 것인가 | R ID | 작업 P1, P2 … (각각 대응 R) |
| 3 | `instruction/` | 작업지시서 (INS) | 구체적으로 무엇을 실행하는가 | P ID | 지시 I1, I2 … (각각 대응 P) |
| 4 | `../scripts/{작업ID}_{slug}/` | 작업 결과물 목록 (TASK, `MANIFEST.md`) | 어떤 코드가 남았는가 | I ID | 파일 목록과 검증 상태, 폴더 전체 해시 |
| 5 | `logs/` | 코드 변경 기록 (LOG) | 코드의 개념·로직이 어떻게 시작해 어떻게 바뀌었는가 | I ID, 직전 LOG | 변경 L1, L2 … 와 지금의 로직, 계보 |
| 6 | `history/` | 작업 기록 (HISTORY) | 무엇이 됐고 무엇이 남았는가 | R·P·I·L 전부 | 추적표, **남은 일 → 다음 작업의 REQ** |

```
작업 N:   REQ ─▶ PLAN ─▶ INS ─▶ TASK(코드) ─▶ LOG ─▶ HISTORY
           R1 ◀── P1 ◀── I1 ◀──── 파일 ◀───── L1 ◀── 추적표          (거슬러 올라가는 대응)
                                                         │ 남은 일
작업 N+1: REQ ◀──────────────────────────────────────────┘
```

## 두 가지 시간축

같은 작업 순서를 두 관점으로 기록한다.

- **`history/` — 일의 시간축.** 작업 순서대로 "목표가 달성됐는가, 무엇이 남았는가"를 쌓는다. 이 폴더만 작업 순서대로 읽으면 프로젝트가 어떻게 흘러왔는지 안다. 새로 온 사람이나 에이전트는 여기부터 읽는다
- **`logs/` — 코드의 시간축.** 작업 순서대로 "`scripts/`(내가 작업하는 코드)·`vendor/`(배포되는 대상의 코드)의 코드가 어떤 개념과 로직으로 시작했고, 이번에 무엇이 왜 바뀌었는가"를 쌓는다. git 브랜치나 커밋을 따라가지 않아도 이 폴더만 작업 순서대로 읽으면 코드가 어떻게 변해 왔는지 안다

MANIFEST와 LOG의 차이: MANIFEST는 **지금 이 폴더에 무엇이 있나**(파일 목록, 검증 상태)이고, LOG는 **어떻게 여기까지 왔나**(이전 → 이후, 이유, 계보)다.

## 코드는 두 곳 — scripts/ 와 vendor/

| | `scripts/{작업ID}_{slug}/` | `vendor/{앱}/` |
|---|---|---|
| 무엇 | 내가 작업하는 코드: 시험, 조사·분석, 초안, 도구 | 배포되는 대상의 코드(application): 다른 기기·고객사·웹/앱에 올라가는 것, SDK, 기존 개발자의 코드 |
| 언제 | 모든 작업 | 요청·REQ에 배포 대상이 있을 때만 (없으면 폴더도 없다) |
| 누가 만드나 | 에이전트가 작업마다 새 폴더 | 앱 폴더는 사용자가 만들고 SDK 등을 넣어 둔다 |
| 추적 | MANIFEST + `tree_hash` 봉인, LOG | 봉인 없음 — **LOG가 유일한 기록** |

흐름: `scripts/`에서 만들고 검증한다 → 구조가 어느 정도 완성되면 그것을 바탕으로 `vendor/{앱}/`에 적용한다 → LOG에 "vendor 적용"(바탕이 된 scripts, 원본에서 달라진 것, 배포 여부)을 적는다. 앱 폴더에는 `README.md`를 둔다 (양식: `_templates/vendor_app.md`).

## LOG에 쓰는 것

- 코드를 만들거나 고친 작업: 변경 내역 표(대상, 종류, 이전 → 이후, 이유, 대응 INS), 지금의 로직, 계보
- 종류: 신규 / 변경 / 복사 후 변경(봉인된 이전 작업 폴더의 코드를 새 폴더로 복사해 고친 것 — 어느 작업의 무엇에서 왔는지 적는다) / 삭제 / vendor 적용(`vendor/{앱}/`을 고친 것 — 바탕이 된 scripts 작업·파일, 사용자가 넣어 둔 원본에서 달라진 것, 기준 커밋·버전, 배포 여부를 적는다)
- "지금의 로직"은 코드를 열지 않고도 흐름을 알 수 있게 쓴다: 입력 → 처리 순서 → 출력, 지켜야 하는 전제
- "계보"에는 직전 LOG의 ID를 적어, 한 코드의 변화를 LOG에서 LOG로 거슬러 올라갈 수 있게 한다
- 코드 변경이 없는 작업도 LOG를 남긴다: 요약에 "코드 변경 없음" 한 줄. 빈 작업이 있어야 시간축이 끊기지 않는다
- 실행 출력·시험 로그 같은 원자료는 여기가 아니라 그 작업의 `scripts/{작업ID}_{slug}/` 안에 둔다. LOG에는 그것이 무엇을 보여 주는지만 적는다

## 이름 규칙

- 문서: `{yyyymmdd}_{순번3자리}_{제목}.md` (날짜·순번이 앞 — 이름순 = 작업 순서). 한 작업의 문서는 `req/` `plan/` `instruction/` `logs/` `history/`에서 **같은 파일명**이다
- 코드 폴더: `scripts/{yyyymmdd}_{순번}_{slug}/`
- 문서 ID: `REQ-`, `PLAN-`, `INS-`, `TASK-`, `LOG-`, `HIST-` + `{yyyymmdd}-{순번}`. 항목 ID: R1, P1, I1, L1 …
- 뼈대는 손으로 만들지 않는다: `python3 scripts/_shared/chain.py new <slug> "<제목>"`

## 양식 — `_templates/`

`chain.py new`는 `_templates/{req,plan,instruction,task,log,history}.md`를 읽어 각 문서의 본문 뼈대를 만든다. `_templates/vendor_app.md`는 `vendor/{앱}/README.md`의 양식이다(도구가 쓰지 않음, 앱 폴더가 생길 때 복사). 머리말(front matter)과 제목 줄은 도구가 붙인다. 표의 열을 바꾸거나 절을 더하고 싶으면 이 파일을 고친다. 이미 만들어진 문서에는 영향이 없다. `_templates/`와 이 `README.md`는 체인 밖이다.

## 체인 — 블록체인처럼, 멱등성과 불변성

```
REQ → PLAN → INS → TASK → LOG → HISTORY → 다음 작업의 REQ → …
```

- 각 문서 머리말의 `prev_hash` = 바로 앞 문서의 `hash`. `hash` = 그 문서 내용의 SHA-256
- TASK(MANIFEST)의 `tree_hash`는 그 폴더의 코드 전체를 묶는다. 코드 한 줄만 바뀌어도 검증이 실패한다
- `LEDGER.md`는 봉인 원장이다: 봉인된 문서의 id·hash를 체인 순서대로 적은 목록. 도구가 뒤에 덧붙이기만 한다

이 폴더의 기록은 블록체인의 원장과 같은 다섯 가지 성질을 지킨다.

| 성질 | 블록체인에서 | 여기서는 | 어기면 |
|---|---|---|---|
| 1. 결정론적 실행 | 같은 입력에는 누가 언제 몇 번 실행해도 같은 결과 | `hash`는 문서 내용만으로, `tree_hash`는 파일 내용만으로 정해진다. 시각·사람·위치·파일명이 들어가지 않는다 | — (계산이 그렇게 돼 있다) |
| 2. 중복 실행 방지 | 논스·UTXO로 같은 거래의 이중 처리를 막는다 | 작업 순번이 논스다: 0부터 빠짐·중복 없이. 같은 제목·slug의 미봉인 작업이 있으면 `new` 거부. `seal`은 봉인된 문서를 건드리지 않아 몇 번 돌려도 같다 | `new` 거부, `verify` "순번이 이어지지 않음" |
| 3. 데이터 무결성 | 중복·위변조가 불가능해 원장 전체를 믿을 수 있다 | 내용 변조 → hash 불일치. 문서 삭제 → 원장에만 남아 드러남. 체인 밖 파일 → 폴더 검사 | `verify` ❌, 종료코드 1 |
| 4. 상태 일치성 | 모든 노드가 처음부터 재실행해도 같은 최종 상태 | `verify`는 저장된 값을 믿지 않고 GENESIS부터 다시 계산해 **head**(마지막 문서의 hash)를 낸다. 같은 `docs/`를 가진 사람은 누구나 같은 head를 얻는다 | head가 보고된 값과 다르면 그 사이에 무언가 바뀐 것 |
| 5. 완결성 | 확정된 결과는 불변으로 영구 기록된다 | 봉인이 확정이다. 다시 봉인하는 기능이 없다. `작성 중` 문서와 문서가 빠진 작업은 봉인되지 않는다. 고칠 일은 새 작업으로 덧붙인다 | `seal --work` 거부, 깨진 체인 위에는 봉인 거부 |

쓰는 순서: 다 썼으면 `python3 scripts/_shared/chain.py seal --dry-run`으로 무엇이 확정되는지 보고 → `seal` → "체인 정상 — 문서 N개, head …". 그 문서 수와 head를 보고에 적는다. 봉인 전까지는 자유롭게 고칠 수 있고, 봉인 뒤에는 오타 하나도 고치지 않는다.

이 다섯 폴더에는 `chain.py new`가 만든 문서만 둔다. 메모·초안·실행 출력은 그 작업의 `scripts/` 폴더에 둔다.

알아 둘 한계: 원장도 `docs/` 안의 파일이라, 문서와 원장을 함께 고쳐 쓰면 이 폴더만으로는 알 수 없다. 그래서 head를 밖에(사용자에게 하는 보고, 또는 git 커밋) 남긴다 — 과거를 고쳐 쓰면 보고된 head와 맞지 않게 된다.
